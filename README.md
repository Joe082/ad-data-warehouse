# Advertising Data Warehouse

A Docker-based advertising data warehouse project that simulates logs generated by multiple application servers and processes them through an end-to-end data engineering pipeline.

The project is designed as a reproducible local environment for demonstrating log collection, message streaming, distributed storage, warehouse modeling, custom Hive UDFs, batch processing, analytical serving, and workflow orchestration.

## Quick Start

Clone the repository:

```bash
git clone https://github.com/Joe082/ad-data-warehouse.git
cd ad-data-warehouse
```

Build the Docker images:

```bash
docker compose build
```

Start the services:

```bash
docker compose up -d
```

Check service status:

```bash
docker compose ps
```

Core services include:

- MySQL
- Kafka
- Flume
- HDFS NameNode
- HDFS DataNode
- Hive Metastore
- HiveServer2
- DataX
- Spark
- ClickHouse
- DolphinScheduler

Initialize the project:

```bash
bash scripts/init_project.sh
```

The initialization script prepares:

- HDFS directories and permissions
- Hive ODS, DIM, and DWD tables
- custom Hive UDFs (`parse_ip` and `parse_ua`)
- ClickHouse database and serving table

The two mock application containers generate runtime advertising logs. Their lifecycle may differ from long-running infrastructure services.

## Hive UDF Initialization

The DWD layer depends on two custom Hive UDFs:

- `parse_ua`
- `parse_ip`

They are initialized automatically by:

```bash
bash scripts/init_project.sh
```

Internally, the project calls:

```bash
bash scripts/init_udf.sh
```

This script:

1. Builds the `parse-ip` Maven project.
2. Builds the `parse-ua` Maven project.
3. Uploads `ip2region.xdb` to HDFS.

The UDF JARs are mounted into HiveServer2 through Docker Compose.

The DWD SQL registers the UDFs with:

```sql
ADD JAR /opt/ad/udf/parse-ip/target/ad-hive-udf-parse-ip-1.0-SNAPSHOT-jar-with-dependencies.jar;

ADD JAR /opt/ad/udf/parse-ua/target/ad-hive-udf-parse-ua-1.0-SNAPSHOT-jar-with-dependencies.jar;

CREATE TEMPORARY FUNCTION parse_ip
AS 'com.atguigu.ad.hive.udf.ParseIP';

CREATE TEMPORARY FUNCTION parse_ua
AS 'com.atguigu.ad.hive.udf.ParseUA';
```

`parse_ip` reads the IP database from:

```text
hdfs://namenode:8020/ip2region/ip2region.xdb
```

## Run ODS

The ODS script loads raw data from HDFS into Hive ODS tables.

Example:

```bash
bash scripts/ods/ad_hdfs_to_ods.sh all 2023-01-07
```

The script exits with an error if an expected HDFS source path does not exist. This is intentional so upstream failures are not silently ignored.

## Run DWD

Run the detailed warehouse layer:

```bash
bash scripts/dwd/ad_ods_to_dwd.sh 2023-01-07
```

The DWD pipeline performs:

- URL and query parameter parsing
- User-agent parsing
- IP geolocation
- invalid-traffic detection
- high-frequency IP detection
- repeated-cycle IP detection
- high-frequency device detection
- repeated-cycle device detection
- dimension enrichment
- partitioned writes into the DWD table

The DWD load uses:

```sql
INSERT OVERWRITE
```

so rerunning the same partition replaces that partition instead of appending duplicate rows.

The exact row count can vary because the mock application servers generate runtime event data.

A successful run should create the partition:

```text
dt=2023-01-07
```

and produce a non-zero row count.

## Data Flow

### 1. Mock application servers

`ad-mock-1` and `ad-mock-2` simulate independent application servers and write access logs to separate mounted directories.

### 2. Flume producer

Flume tails the application logs and sends events into Kafka.

### 3. Kafka

Kafka provides buffering and decouples log generation from downstream ingestion.

### 4. Flume consumer

The downstream Flume agent consumes Kafka events and writes them to HDFS.

### 5. HDFS

HDFS stores raw files used by the Hive ODS layer.

### 6. Hive ODS

The ODS layer preserves raw source structure.

### 7. Hive DWD

The DWD layer cleans, parses, enriches, and labels event-level data.

### 8. Hive DIM

Dimension tables provide reusable descriptive attributes.

### 9. Spark / ClickHouse

Spark is used for the Hive-to-ClickHouse transfer path, and ClickHouse provides an analytical serving layer.

### 10. DolphinScheduler

DolphinScheduler orchestrates ETL tasks and dependencies.

## Reproducibility Design

Several parts of the project are intentionally built inside Docker images so a new user does not need pre-built local artifacts.

### DataX

The DataX image downloads DataX during Docker build instead of requiring a local `datax.tar.gz`.

### Flume interceptor

The custom Flume interceptor is built in a Maven build stage and copied into the Flume runtime image.

### Spark application

The Hive-to-ClickHouse Spark application is built inside the Spark Docker image.

### ClickHouse schema

The ClickHouse database and serving table are initialized from repository-managed SQL through:

```bash
bash scripts/init_clickhouse.sh
```

This avoids relying on Spark JDBC to auto-create a `MergeTree` table without an explicit `ORDER BY` clause.

### Hive UDFs

Hive UDFs are built and installed by the project initialization flow:

```bash
bash scripts/init_project.sh
```

The initialization flow invokes `scripts/init_udf.sh`, and the resulting JARs are mounted into HiveServer2.

## Troubleshooting

### HiveServer2 exits during startup

The Docker Compose configuration should wait for MySQL health before dependent services start.

If HiveServer2 still exits with a MySQL connection error, verify MySQL manually:

```bash
docker exec ad-mysql mysql -uroot -pmysql -e "SELECT 1;"
```

Then recreate the Hive services if necessary:

```bash
docker compose up -d --force-recreate hive-metastore hiveserver2
```

---

### `Invalid function parse_ip` or `Invalid function parse_ua`

The UDFs are temporary Hive functions and exist only within the session in which they are registered.

The DWD SQL registers them automatically.

If testing manually, run the corresponding `ADD JAR` and `CREATE TEMPORARY FUNCTION` commands in the current Beeline session.

---

### `parse_ip` returns null fields

Confirm that the IP database exists in HDFS:

```bash
docker compose exec -T namenode \
  hdfs dfs -ls /ip2region/ip2region.xdb
```

You can also verify that the local and HDFS files are identical:

```bash
shasum -a 256 udf/parse-ip/ip2region.xdb

docker compose exec -T namenode \
  hdfs dfs -cat /ip2region/ip2region.xdb | shasum -a 256
```

---

### DWD SQL file not found

The DWD script resolves the repository root dynamically, so it can be run directly from a cloned repository:

```bash
bash scripts/dwd/ad_ods_to_dwd.sh 2023-01-07
```

It no longer depends on a machine-specific `/opt/ad` host path.

## Known Limitation

The `dim_crawler_user_agent` table is created during Hive initialization.

The original crawler user-agent seed dataset is not currently included in the repository, so on a completely fresh environment this dimension may initially be empty.

The rest of the DWD pipeline remains functional, but crawler-user-agent-based invalid-traffic detection will not match records until that seed dataset is loaded.
